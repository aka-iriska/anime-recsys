# Выгрузка Shikimori для рекомендаций

Проверено запросами к живому API 2026-09-24. Исходный код схемы Shikimori [архивирован](https://github.com/shikimori/shikimori), поэтому для новых полей нужна отдельная проверка запросом.

| Таблица | Содержание | Применение |
| --- | --- | --- |
| `users_rates.csv` | Текущая запись пользователя об аниме: `user_id`, `anime.id`, `score`, `status`, `episodes`, `rewatches`, `createdAt`, `updatedAt` | Основной сигнал предпочтений; `score=0` означает отсутствие оценки |
| `users_history.csv` | События изменений списка с `created_at` и `anime_id` | Время действий на сайте, когда история открыта; не подтверждает просмотр в этот момент |
| `history_access.csv` | Доступность истории по пользователю | Отличить закрытую историю (`403`) от пустой |
| `anime.csv` | ID, названия, описание, формат, статус, число серий, даты релиза, `franchise` и прочие метаданные | Каталог кандидатов и признаки контента |
| `genres.csv`, `anime_genres.csv`, `anime_studios.csv` | Жанры, теги и студии | Признаки контента |
| `anime_relations.csv` | Связи `anime_id → target_id`, `target_type`, `relation_kind` | Продолжения, приквелы и другие связи; для аниме-рекомендателя фильтровать `target_type=Anime` |
| `anime_chronology.csv` | Позиции в последовательности, которую возвращает API для франшизы | Анализ связанной серии; порядок API не следует автоматически считать рекомендуемым порядком просмотра |
| `uncatalogued_interaction_anime.csv` | ID из пользовательских записей, отсутствующие в новом каталоге | Проверка полноты соединения таблиц |

Схема API: [UserRate](https://github.com/shikimori/shikimori/blob/master/app/graphql/types/user_rate_type.rb), [Anime](https://github.com/shikimori/shikimori/blob/master/app/graphql/types/anime_type.rb), [поля Anime и Manga](https://github.com/shikimori/shikimori/blob/master/app/graphql/types/concerns/ani_manga_fields.rb), [Related](https://github.com/shikimori/shikimori/blob/master/app/graphql/types/related_type.rb), [запрос каталога](https://github.com/shikimori/shikimori/blob/master/app/graphql/queries/animes_query.rb).

Для `chronology` сервер разрешает только один объект за запрос. Поэтому скрипт берёт один тайтл для каждой франшизы, которая встретилась в пользовательских записях, а при отсутствии имени франшизы — отдельные оценённые тайтлы со связями с другими аниме. Первые 50 тайтлов и запрос одной хронологии успешно проверены перед запуском. Все ответы API сохраняются как промежуточные JSON; каталог собирается страницами по 50 и продолжается после остановки.

Постраничный запрос пропустил 6148 ID аниме из пользовательских списков, хотя запрос по конкретным ID вернул все 6148. `backfill_catalog.py` догрузил их пакетами по 50 с контрольными файлами в `anime_by_id_batches/`, пересобрал таблицы каталога и обновил хронологию. Итог: 30 133 уникальных аниме, 40 285 связей и 50 439 строк хронологии. Для всех 694 673 записей в текущих списках 2000 пользователей найдено аниме в каталоге; `uncatalogued_interaction_anime.csv` пуст.

Исходные 1151 пользователей взяты из старого CSV. Для нового снимка подготовлена когорта из 2000 ID: исходные 1151 плюс 849 пользователей, случайно отобранных из списка активных с seed=42. Это выборка активных пользователей сайта, а не всех зарегистрированных. Отдельно собираются текущие REST v2 списки аниме и избранное каждого пользователя; для 849 новых пользователей дополнительно собираются события истории; историю исходной группы повторно не скачиваем. Избранное не имеет даты добавления и не подходит как исторический признак без явного времени снимка. Глобальные агрегаты, персонажей и персон пока не выгружаем.

## Проверки после завершения

1. Убедиться, что статус запуска равен `complete`.
2. Посчитать строки и уникальные `user_id`/`anime_id` во всех основных CSV.
3. Проверить уникальность `anime.id`, долю отсутствующих ID из `users_rates`, число пользователей с закрытой историей.
4. Проверить связи и хронологию на нескольких известных франшизах вручную.
5. Решить, можно ли вообще построить временное разделение по истории: `createdAt`/`updatedAt` текущей записи не равны дате просмотра.

## Дополнительные возможности API (проверка 2026-09-24)

[Официальная документация](https://shikimori.io/api/doc) перечисляет REST v1/v2, но рекомендует GraphQL. Для нескольких сигналов пока нужен REST.

| Источник | Что даёт | Решение для проекта |
| --- | --- | --- |
| [`GET /api/stats/active_users`](https://shikimori.io/api/doc/1.0/stats/active_users.html) | ID пользователей с хотя бы одним завершённым аниме, активных за последний месяц. При подготовке выборки живой запрос вернул 94 928 ID. | Хороший пул для нового отбора пользователей. Нельзя считать его случайной выборкой всех пользователей. |
| [`GET /api/users/:id/anime_rates`](https://shikimori.io/api/doc/1.0/users/anime_rates.html) | Текущий список аниме пользователя; лимит до 5000 записей за запрос. | При расширении аудитории сравнить с нашим GraphQL-пагинатором: потенциально один запрос вместо многих страниц. |
| [`GET /api/users/:id/favourites`](https://shikimori.io/api/doc/1.0/users/favourites.html) | Избранные аниме и персонажи. В пробе из пяти активных пользователей аниме в избранном были у одного. | Дополнительный сильный положительный сигнал, но разреженный и без даты добавления. |
| [`GET /api/animes/:id/similar`](https://shikimori.io/api/doc/1.0/animes/similar.html) | Похожие аниме по версии сайта; для ID 1 вернулось 166 элементов. | Отдельный внешний baseline или граф соседства; текущий результат нельзя без проверки использовать в историческом offline-тесте. |
| [`GET /api/animes/:id/roles`](https://shikimori.io/api/doc/1.0/animes/roles.html) и GraphQL `characterRoles`/`personRoles` | Актёры озвучки, режиссёры, персонажи и другие роли. | Потенциальные контентные признаки для холодных тайтлов; потребуют больше запросов и отдельной оценки пользы. |
| [`GET /api/animes/:id/franchise`](https://shikimori.io/api/doc/1.0/animes/franchise.html) | Узлы и направленные связи франшизы. | Можно сравнить с уже собираемыми `related` и `chronology`, если их будет недостаточно для порядка серий. |
| [`GET /api/users/:id/friends`](https://shikimori.io/api/doc/1.0/users/friends.html), [`clubs`](https://shikimori.io/api/doc/1.0/users/clubs.html) | Социальные и клубные связи. | Возможны социальные признаки, но для первого рекомендателя их ценность и покрытие неизвестны. |
| [`GET /api/achievements`](https://shikimori.io/api/doc/1.0/achievements/index.html) | Достижения пользователей по старой документации. | Пробный живой запрос вернул 404; не закладывать в пайплайн без дополнительной проверки. |

У GraphQL в живой схеме есть корневые запросы `animes`, `characters`, `contests`, `currentUser`, `genres`, `mangas`, `people`, `userRates`, `users`. В `userRates` доступно также поле `text`; оно не вошло в текущую выгрузку и потребует отдельной оценки заполненности и полезности. Отдельных событий показов рекомендаций и кликов этот API не предоставляет: для такой онлайн-оценки понадобится собственное логирование приложения.

**Итоговый снимок:** выгружены списки и избранное 2000 пользователей, история 849 новых и история 1124 из 1151 исходных пользователей; у остальных 27 история недоступна. Когорта, список активных ID и время снимка сохранены в `shikimori_expanded_users_2000_2026-09-24/cohort_manifest.json` и `active_user_ids.json`; на момент выбора пул содержал 94 928 ID. На пробе пользователь с 458 записями целиком помещался в один ответ REST v2. Лимит сайта — [90 запросов в минуту](https://shikimori.io/api/doc). Список похожих аниме не используется как метка для обучения или оценки нашей модели.

Формальную [неофициальную OpenAPI 3.1.1-схему](https://github.com/MAKS11060/openapi) также просмотрели: в опубликованной версии на дату проверки 49 путей. В ней есть `animes/:id/similar` и `v2/user_rates`, но отсутствуют документированные и работающие `stats/active_users`, `users/:id/history`, `users/:id/favourites`. Поэтому её удобно использовать как указатель, но для выбора источников сверяться с официальной документацией и пробным запросом к живому API.
